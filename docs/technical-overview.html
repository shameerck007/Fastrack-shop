1. What this application is

FasTrack Shop is a Phase 1 MVP quick-commerce grocery delivery app with four user roles:

  • Customer — browse categories, search products, cart, checkout, track orders, delivery OTP.
  • Admin — catalog/inventory management, order oversight, merchant approval, BI-style dashboard.
  • Merchant — sell products under the marketplace, manage own product listings.
  • Rider — view assigned deliveries, update status, OTP-verified drop-off, live location sharing.

The original business requirements live in BRD_shop.pdf in the repo root.

Deploying a change

git pull
npm install                  # only if dependencies changed
npm run build:vinext         # builds the Cloudflare/Workers bundle
npm run deploy:vinext        # uploads + activates the new Worker version
There is no CI/CD pipeline. Deploys are manual, run from a developer's machine with Wrangler already authenticated to the Cloudflare account (npx wrangler whoami to check). Pushing to GitHub does not update the live site by itself.

Local development

npm install
npm run dev          # plain Next.js dev server — fastest for UI work, no Workers runtime
npm run dev:vinext   # vinext dev server — closer to production behaviour
npm run start:vinext # runs the actual built Worker locally via `wrangler dev`
                      #   — use this to test anything Workers-specific
                      #   (KV, edge cache, cold-start behaviour) before deploying

5. Data layer (Supabase)

  • Schema + Row Level Security policies: supabase/migrations/0001_init.sql
  • Sample data: supabase/seed.sql
  • Roles are stored on the profiles table (customer, admin, merchant, rider), set by a handle_new_user trigger on signup, then promoted manually via SQL — see README for the exact commands.
  • Auth cookies are handled by @supabase/ssr. Server-side code reads the session via src/lib/supabase/server.ts; client-side/browser code uses src/lib/supabase/client.ts.
Auth URL configuration lives only in the Supabase dashboard (Authentication → URL Configuration), not in code. If the domain ever changes, that setting must be updated manually — Site URL and Redirect URLs both need https://shop.fastrack.cloud.

7. Known constraints — read before touching performance-sensitive code

Workers Free plan: 10 ms CPU budget per request

Cloudflare Workers Free gives each request 10 milliseconds of active CPU time (network/database wait time doesn't count, only JS execution). A cold-started isolate has to parse and evaluate the app's JS before serving anything, which eats into that budget. This previously caused intermittent "Error 1102 — Worker exceeded resource limits" failures, especially on mobile after the app had been idle (a fresh isolate).

Mitigations already in place (as of this document):

  • Per-user data (cart count, login state, "Buy Again") was moved out of every page's server render into small client-side components (UserHeaderActions.tsx, BuyAgainSection.tsx) so most pages no longer call Supabase auth on every server request.
  • Cloudflare's Workers Cache API and a KV data cache are enabled (vite.config.ts), so repeat requests to the same page can be served from the edge without invoking the Worker at all.
  • Build-time route prerendering is enabled where the adapter's static analysis allows it.
If CPU-limit errors reappear, do not add more server-side Supabase calls to components rendered on every page (headers, layouts, nav). Push personalization into client components that fetch after the initial render, and verify locally with npm run start:vinext (real Workers runtime, not plain next dev) before deploying. Live production behaviour can be watched with npx wrangler tail fastrack-shop --format pretty. The permanent fix, if this keeps being a problem, is upgrading to Workers Paid ($5/mo, 30s+ CPU budget) — this was explicitly deferred by the project owner, not ruled out permanently.

vinext is a beta adapter

vinext (Cloudflare's Next.js-on-Workers adapter) is pre-1.0 at the time of writing. Its static-analysis-based route classification (which routes get prerendered vs. run as SSR) is imperfect — don't assume a route is static just because it looks static; check the build output (npm run build:vinext prints a route classification table).

9. What's not built yet

Per the BRD roadmap (§§26–30, 33–34): multi-vendor marketplace polish, promotions/coupons UI, loyalty/wallet, AI search and shopping assistant, delivery route optimization, subscriptions. The database schema already has room for promotions, reviews, and payments/refunds tables to build on — check supabase/migrations/0001_init.sql before adding new tables for these features, they may already partially exist.
